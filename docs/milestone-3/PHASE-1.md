# Milestone 3, Phase 1: durable venture record, deal flow, lessons memory

Status: implemented and tested against PostgreSQL 16 (CI service container and local). Production database: **pending one Vercel dashboard step** (see Deploy).

## What was built (behind the existing interfaces)

Milestone 1 and 2 endpoints (`/api/curate`, `/api/pitch`, `/api/ask`, `/api/extract`, `/api/vet-repos`) are unchanged. Persistence sits behind them:
- `POST /api/v1/ventures/:id/runs` calls the same `handleCurate`.
- Pitches are generated by the same `buildScript`.
- Answers come from the same `answerQuestion`.

| Area | Endpoints (`/api/v1/...`) | Tables |
|---|---|---|
| Auth | `auth/signup`, `auth/login`, `auth/logout`, `auth/me` | `fe_users` (scrypt), `fe_sessions` (token stored as SHA-256 only) |
| Venture record | `ventures`, `ventures/:id/runs`, `ventures/:id/pitches`, `ventures/:id/history` | `fe_ventures`, `fe_runs` (full M1 result incl. receipts), `fe_pitches` (versioned, `facts_hash`) |
| Deal flow | `ventures/:id/investors`, `.../invitations`, `.../invitations/:iid/revoke`, `.../sessions`, `.../investors/:iid/stage`, `invite/open`, `invite/ask` | `fe_investors`, `fe_invitations`, `fe_pitch_sessions`, `fe_qa`, `fe_stage_transitions`, `fe_followups` |
| Lessons | `lessons` (POST/GET) | `fe_lessons` |
| Audit | included in `history` with chain verification | `fe_audit_events` |

UI: `/studio.html`. Founders sign in; investors open `/studio.html#invite=<token>`.

## Governance requirements → mechanism

| Requirement | Mechanism | Test |
|---|---|---|
| Tenant isolation | `FORCE ROW LEVEL SECURITY` on every tenant table, keyed on a per-transaction `app.user_id`. Every request transaction runs `SET LOCAL ROLE fe_app` (no superuser, no BYPASSRLS, minimal grants). A guard refuses to serve if the effective role could bypass RLS. Holds even when the connection user is a superuser or a managed owner role with BYPASSRLS | Other founder gets 404 and an empty list. Raw query with no tenant returns 0 rows. Forged cross-tenant insert is rejected by policy |
| Immutable audit history | Triggers reject UPDATE/DELETE/TRUNCATE on audit events, runs, pitches, Q&A, stage transitions and lessons. Audit events are SHA-256 hash-chained per tenant | All three operations rejected. An owner who disables a trigger and edits a row is **detected**: `audit_chain.intact = false` at the edited event |
| Explicit authorization for investor invitations | The founder must submit a statement beginning `I authorize inviting <investor> to pitch v<n>`. Accredited access also requires `verified_by` (third-party verification reference), enforced by API and a DB CHECK. Tokens are random, shown once, stored hashed, expiring and revocable | Missing or wrong statement → 400. Accredited without `verified_by` → 400. Revoked or unknown token → 401. Token never appears in history |
| No autonomous securities transactions | No offer, negotiation, subscription, payment or settlement code. Automatic stage moves only go forward and never into `founder_meeting`, `interest_recorded` or `passed`, which need a founder action with a note | Backward move → 409. Stage history shows `system:` vs `founder:` actors |
| Lessons inform, never authorize | A lesson needs evidence (a stored run id or a receipt hash inside one). It is attached to later runs as `lessons_consulted` with `advisory: true` and changes no behaviour. Corrections supersede; nothing is edited | Bogus evidence → 422. Next run lists the lesson as advisory |

## Acceptance criterion (passes)

> A founder creates a venture, runs curation, generates a pitch, invites an investor, records a Q&A session, advances the deal stage and retrieves the complete evidence history after a fresh login.

`test/studio.test.ts`, first test. The history after re-login contains:
- 2 runs with full receipts
- pitch v1
- the investor's stage path researching → invited → viewed → qa → followup → founder_meeting
- 1 invitation, with no token
- 2 sessions, 3 Q&A turns, 1 follow-up
- an intact audit chain covering every action

## Open items (not resolved by this phase)

1. **Securities counsel review of the operating model.** Avoiding transaction-based compensation reduces broker-dealer risk, but it does not by itself establish an exemption. Platform conduct (solicitation, recommendations, involvement in negotiations, handling of funds) also matters. Counsel must review before investors are invited at scale.
2. ~~Least-privilege database role~~ **Done (migration 002).** Requests run as `fe_app`, which has SELECT/INSERT plus three column-level UPDATEs and cannot ALTER, TRUNCATE or DELETE evidence. Found by CI: the postgres image user is a superuser, which bypasses RLS, so isolation must not depend on the connection role. Remaining: the owner credential (used for migrations) can still disable triggers; the hash chain detects that.
3. **Login throttling and account recovery** are not built.
4. **Expired-invitation path** is enforced in SQL and code, but covered only by the revocation test.
5. **Investor accounts** (vs. bearer invitation links) are a later phase.

## Deploy

1. In Vercel → project **founder-engine** → Storage → Create Database → choose a Postgres provider (e.g. Neon) → connect it to the project for Production and Preview. This injects `DATABASE_URL` / `POSTGRES_URL`.
2. Redeploy. Migrations run automatically on the first `/api/v1` request. Set `FE_AUTO_MIGRATE=0` to manage them yourself with `node dist/src/cli.js migrate`.
